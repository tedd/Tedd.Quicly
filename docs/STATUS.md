# Implementation status

Last updated 2026-09-30. Test counts are totals across both target frameworks (net11.0 + net10.0), measured per project and
per framework on the branch `fix/localhost-drops` — `main` at 19cb971 (the admission fix: the Hello waits for a
definitive datagram capability and the admission deadline also binds late Hello, HelloAck and policy completion;
[CHANGELOG.md](../CHANGELOG.md)) plus the localhost-drop fixes and their reviews ([RELEASE-NOTES.md](RELEASE-NOTES.md)): the sequence clock for idle keys, expiry from the first
scheduler pass, the transport outcome statistics, the bounded drain backlog of undrained unreliable channels and `Release`
after `Dispose`; and, merged last (e21c30f), the MsQuic held-stream resume fix: a stream the receiver held (receive ring
full, budget used up, application not polling) and resumed with zero bytes could stall for good, its messages reported
`Delivered` to the sender — a hold is now answered to MsQuic as a partial consumption and the resume only re-enables
receiving. One defect that loses reliable messages is known and not fixed at this commit: a `ReliableUnordered` receiver
that falls far behind resets group streams the sender already reported `Delivered` (see Remaining). Line coverage figures are from the module reviews (Microsoft.Testing.Extensions.CodeCoverage,
cobertura; the Core rows were re-measured at the wave C2 merge) and were not re-measured after the hot-path pass or the
2026-09-30 fixes; no benchmark was re-run for those fixes either (see Remaining). The Core, Testing, Transport.MsQuic,
Server and Client rows were measured at e21c30f, unfiltered, in Debug, and all five projects pass on both frameworks there;
the other rows were not re-measured for this update. (The certificate/TLS tests had failed on this machine since test roots with
fixed names piled up in the Windows intermediate store past its 50-per-name limit; roots are now unique and removed after use.)

## Remaining

| Wave | Content |
|---|---|
| group streams | **Known defect, not fixed in this release: a `ReliableUnordered` channel loses whole groups when the receiver falls far behind.** The sender frees a group's stream when QUIC acknowledged it while the receiver still counts it open; the sender then opens more group streams than the receiver accepts (`MaxGroups`; over MsQuic a client's handshake grant of 1 024 unidirectional streams, `MsQuicTransportOptions.ClientPeerUnidiStreamCount`, also exceeds the receiver's records), the receiver resets them `LimitExceeded` and the sender has already reported their messages `Delivered`. Visible as `PeerStatistics.StreamsReset` on the receiver only ([TROUBLESHOOTING.md](TROUBLESHOOTING.md), "Reliable channels"). The receive-limit fix is in review on its own branch and ships in the next release. |
| D1b | Per-channel receive credit for `ReliableOrdered` / `ReliableUnordered` channels without a handler (designed, being built on its own branch). **Until it lands an undrained reliable channel still holds the receive ring**: once the drain-queue pool is full its next message is held, every stream channel of the peer is back-pressured, datagrams of ring channels are dropped on arrival, responses wait and `HasPendingWork` stays set, until the application drains the channel or registers a handler (PROTOCOL.md §7, session-layer.md §4.4). |
| drop fixes, follow-ups | Left open by the 2026-09-30 fixes, all documented where they apply: no benchmark was re-run for the 2026-09-30 changes, neither the session benchmarks nor, after the held-stream change, the MsQuic transport ones ([msquic-transport](benchmarks/msquic-transport.md)) (`SessionEndToEndBench.Sequenced64KeyedExpiring` for the expiry stamp, the client-poll benchmark for the drain queues, `RequestResponseBench` for the per-request clock read; to be measured on `main`, one session at a time); a sequenced datagram that more than a reorder window of later messages overtook in the sender's transport queue is still delivered out of order once after 2 s of quiet — the sender-side remedy (no priority overtaking inside one sequenced channel, or never packing a sequenced message into a container that loses cancel-on-blocked) is not built; `ReliableLatest` still loses the values of 2^31 consecutive versions with no arrival in between, and an old-epoch group stream that ends after an epoch reset still feeds its version into the new clock; expiry deadlines are not published to `NextFlushDeadlineMicros` (a held-back message is dropped at the next pass after its deadline) and the time a thread-safe send waits in the MPSC front is not counted; the `ReliableLatest` 30 s version budget and retry timers still use the pass stamp; the drain-queue node pool stays capped at 1 024 (a host that cannot drain once per Poll keeps at most that backlog); the exact condition under which MsQuic cancels a flagged datagram is documented from msquic.h only; with default `AllocatorOptions` a peer reported `OutOfReceiveBuffers` at 4 096 outstanding 64-byte receive blocks under a 16 MiB receive budget, and not with `FreeListShards = 1` (seen in the second review, not investigated: it looks like the 64-byte class being limited to one shard's share on the renting thread, and it would limit the "raise `ReceiveBudgetBytes`" advice for small messages); `QuiclyServer.PollAll` still keeps a slot marked whose probe was clear, although the probe now re-arms the peer's signal itself; the work-signal race tests (`ReviewRecheck2R1PollRearmTests`) only bite in a Release build, so a Debug-only test run does not guard the fenced re-arm in `Poll` — and CI does not run the Core tests in Release: its test step runs only Http3.Tests, Testing.Tests and Acme.Tests (Release, net10.0), so that regression is guarded by nothing but a manual Release run of Core.Tests; from the held-stream review, a WebTransport stream whose preamble and FIN arrive before the session is established is replayed to Core but never resumed, so it never ends (older than this release, confined to the peer's own connection). |
